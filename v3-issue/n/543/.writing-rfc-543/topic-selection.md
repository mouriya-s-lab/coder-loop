# 选题确定

## 素材结构

素材属于多中心一主题：声明模型、observer、gate、payload、journal、具名绑定、join/reopen 与可观测性是不同能力，但都服务于同一问题——如何让 coder-loop 在不内置业务策略的前提下，安全地把生命周期事实和调度决定开放给外部脚本。用户已明确要求解释“实现什么、为什么实现”，因此不另选旁支主题。

## 五个方向

1. **需求侧**：解释用户为何不能只靠现有 agent phase 或事件日志完成检查—修复—继续的闭环。形态为单中心，匹配度高。
2. **供给侧**：逐层说明 RFC 提供的声明、执行、决策、持久化和恢复能力。形态为多中心一主题，信息密度最高。
3. **差异化**：重点解释 observer 与 gate 的职责分离、策略外置、identity 分层及外部副作用非保证。形态为多视角，能体现本 RFC 与普通 hook 系统的差异。
4. **可论证深度**：以“事实进入系统—脚本执行—决策生效—崩溃恢复—审计复盘”为因果链。形态为多中心一主题，论证链完整。
5. **收获感**：读者能够判断每项机制解决的具体失败模式，并区分当前 main 已实现的基础与 RFC 尚待实现的运行闭环。形态为单中心，实用性高。

## 对抗分析

- 只列功能清单：不通过。它不能解释为何需要 journal、fingerprint、typed ingress 等看似复杂的机制。
- 只讲操作员“检查—修复—继续”场景：不通过。它会遗漏声明安全、恢复和跨 RFC 接缝。
- 按历史 issue 或提交时间写时间线：不通过。旧 issue 边界已经被证明会造成职责混乱，也不符合用户要求的独立思考。
- 按运行因果链解释能力并区分现状、目标和非保证：通过。它能覆盖所有核心机制，同时避免把设计目标误写成现有实现。
- 把文档写成概要或执行计划：不通过。用户明确要求完整解释，不允许概要；本文也不负责重拆 issue。

## 最终方案

采用多中心一主题的分析报告。核心判断是：RFC #543 实现的不是一组散落的脚本回调，而是一条从生命周期事实到可恢复调度决定的扩展协议；其必要性来自三个约束同时成立——策略必须留在引擎外、调度决定必须可靠、脚本失败不能破坏调度内核。正文以运行因果链组织，完整区分“main 已有基础”“RFC 要补齐的能力”“明确不保证的边界”。
