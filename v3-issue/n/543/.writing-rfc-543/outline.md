# 大纲

## 读者画像

- **知识边界**：了解 coder-loop 的 daemon、chain、item、phase 与 preset；知道 hook 和持久化状态机的基本概念，但未必了解本 RFC 的身份分层和跨 RFC 边界。
- **阅读动机**：需要准确理解 RFC #543 最终要改变什么、每项机制解决什么问题，以及哪些能力当前其实还不存在。
- **预期收获**：能沿一次事件或 gate evaluation 的完整生命周期解释系统行为，判断 observer、gate、journal、binding、reopen 各自的责任，并识别非保证与外部依赖。

## 核心论点

RFC #543 实现的是一条策略外置、类型闭合、可恢复且可审计的生命周期扩展协议，而不是普通的“事件发生后运行脚本”。

## 逻辑线

1. 先区分 main 已实现基础与 RFC 目标，避免把声明存在误认为执行闭环已经存在。（事实）
2. 从操作员检查—修复—继续场景说明仅有事件日志为何不足。（因果推理）
3. observer 解决“看见并旁路执行”，gate 解决“在明确决策点阻止推进”。（职责对比）
4. payload、identity、journal 和恢复解决跨重启的一致性与可追溯性。（递进因果）
5. 四层声明与具名绑定解决全局治理、preset 可分发和实例覆盖的张力。（约束分析）
6. script join/reopen 把脚本判断接到容器推进，但权威 target/claim/budget 仍由 RFC-1 提供。（边界分析）
7. 可观测事件、status 和 diagnostic 使 hook 自身成为可调查对象，同时以零自反防止递归风暴。（因果与安全）
8. 外部副作用非保证、GitHub 语义排除和跨 RFC blocker说明该协议刻意不解决什么。（范围收束）
9. 最后解释这些机制如何共同服务于策略外置，而不是把引擎变成策略框架。（结论）

## 读者追问链

- 当前到底已经有什么？→ 先列 main 基础和明确缺口。
- 为什么有声明还不够？→ 说明真实场景需要执行与调度控制。
- 为什么分 observer 和 gate？→ 说明旁路与阻塞的失败语义不同。
- 为什么不能脚本退出码直接决定？→ 引出 typed decision、合法组合和多层合成。
- 为什么还需要 journal 和多个 identity？→ 引出崩溃窗口、重放与审计。
- preset 如何安全引用本机脚本？→ 引出具名 gate binding。
- reopen 为什么不能由 hook 自己改几张表？→ 引出 RFC-1 authority。
- 并发脚本破坏外部系统怎么办？→ 说明脚本作者责任和引擎非保证。
- 这些复杂机制最终换来了什么？→ 回到策略外置而可靠的扩展协议。

## 结构与节奏

采用问题驱动的分析报告结构：Background → Findings → Analysis → Conclusions。

1. **问题边界与现状（慢）**：严格区分已实现与待实现。
2. **为什么普通 hook 不够（慢）**：完整展开操作员场景及失败模式。
3. **声明与能力发现（中）**：四层声明、ADT、operator-only。
4. **Observer 执行链（慢）**：payload、process ownership、并发、diagnostic。
5. **Gate 决策链（慢）**：decision ADT、决策点、AND、hold、fingerprint。
6. **持久化与恢复（慢）**：evaluation、delivery、attempt、epoch、journal。
7. **具名绑定与可分发 preset（中）**。
8. **Join/reopen 接缝（慢）**：#543 与 RFC-1/2 的责任线。
9. **可观测性和安全边界（中）**。
10. **为什么这些机制必须组合出现（慢）**。
11. **明确非保证与当前 blocker（中）**。
12. **结论（慢）**：回扣核心论点，不写实施建议。

## 工作标题与承诺

标题：**RFC #543：生命周期扩展协议实现了什么，以及为什么必须这样实现**

标题承诺读者将获得完整的能力与动机解释；第 1–11 节逐项兑现，不以概要、历史时间线或 issue 清单替代论证。

## 对抗检验

- 逻辑链无跳步：每项机制均由前一层暴露的失败模式引出。
- 标题承诺完整兑现：既说明“实现什么”，也逐项说明“为什么”。
- 不按旧文档章节顺序组织，不复制条款表；结构来自运行因果链。
- 现状、预期地基与外部依赖分开陈述，不会把未实现能力写成既成事实。
- 不写执行概要；正文必须保留论证过程、边界和失败场景。
