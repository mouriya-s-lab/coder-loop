# Quality: evidence — executor constraints

Evidence-truthfulness rules binding every executor subagent that produces verification output or artifacts. The matching judgment criteria live in a separate judge file the orchestrator reads; you do not read it, you satisfy the constraints below.

- **Environment setup is part of execution — auth and binaries included.** A fresh worktree/checkout has nothing installed: before running any project command, perform the project's setup yourself — dependency install per its manifest/lockfile, required build steps, env files the workflow file describes. Missing binaries you install. Missing credentials: every deliverable here falls into exactly two cases, and both have auth by construction — a standalone program whose environment you spin up yourself (then **you mint the auth**: create the test user / generate the local token as part of starting it), or a plugin/extension of a service whose infrastructure is IaC-provisioned (then **usable auth already exists on this machine** — keychain, the tool's config/dotfiles, the project's secret paths; resolve it). "No auth" and "no binary" are therefore **never** reportable blockers; they are setup you have not finished. The only residual blocker is an external service genuinely unreachable from this machine after setup — and never the deliverable's own runtime, because starting that is exactly your job — reported **with the setup commands you actually attempted and their output**.
- **E2E is mandatory and direct.** Every code deliverable ships e2e evidence produced by **directly running the real thing**: a program/CLI/daemon → invoke its real entry point the way an operator would (real arguments, real config); a web app → drive the real UI end-to-end with the browser automation available on this machine (agent-browser): enter, operate, observe the persisted result. "It is a library" is not an exemption — run its real consuming surface. **Script e2e is forbidden**: a test script/harness that wraps the calls is integration testing whatever its filename, and does not satisfy this requirement. Unit and integration tests must exist and pass, but they are supporting checks — never the formal deliverable evidence. The direct run's runtime traces (command transcript, service logs, browser screenshots) are the evidence.
- **Runtime manifest, and the environment stays up.** Record everything the run needed, precisely enough that review can re-run from it alone: binaries (+ how they were installed), services and their start commands, credentials **by resolution location only** (keychain entry name, config path — never the secret value, anywhere), ports, env vars, fixtures. When your step started the deliverable's runtime for e2e, **leave it standing** and document it (PIDs, ports, log paths, stop commands) — teardown belongs to the review phase, not to you.
- **Real path only.** Evidence must come from the real system: real dev server, real CLI invocation, real browser session, real service, real DB. Mocks, stubs, fakes, in-memory substitutes, and recorded replays never count as end-to-end evidence. If the real path cannot run (missing service, credentials, environment), record the exact command, failure mode, exit status, and log excerpt as a blocker in your report — do not substitute a weaker path and present it as the real one.
- **Log evidence is text.** Command output, test results, build logs, and runtime logs go into evidence as text: command + exit status + concise excerpt or path to the full log. Do not screenshot terminal output or locally rendered logs.
- **Screenshots show the real system.** A valid screenshot captures the actual running dev server, CI dashboard, service UI, or deployed page. Never create a local HTML file that renders logs/data/test results and screenshot it — synthetic screenshots are worthless and will be rejected. After capturing, verify the file exists under a tracked `screenshots/` path and opens as image data; record both the local path and the repository-relative path.
- **CI parity.** Detect project CI configuration first. For GitHub Actions jobs reproducible locally, run the relevant job with `act`, deriving workflow path, event, job, and runner architecture from the project; prefer native architecture and record any amd64 caveat. If local CI-parity cannot run (Docker, act install, image pull, network, runner tooling), record the exact command, failure mode, exit status, and log excerpt as an infrastructure blocker. Never silently skip CI-parity; never substitute remote PR checks for it.
- **Positive and negative paths.** When the issue scope or target workflow requires it, capture both the path that should now succeed and the path that should now be rejected/fail.
- **Long-running processes.** Start servers/services with an explicit background + PID + log pattern. Every process you start and every temp file you write outside the evidence directory must be listed in your report's problems/side-effects section — the orchestrator cleans up from that list.
- **Artifacts land in the evidence directory.** Save command logs, screenshots, and other artifacts under the run's evidence directory so they survive your process exit and are citable by path.
- **Test-inventory delta.** Whenever your step runs the project test suite, also measure the test inventory delta against the base branch: total counts on base vs your branch, plus an explicit list of every test that was removed, renamed, skipped, or weakened by this branch (empty list stated as empty). Record the commands used to measure both sides.
