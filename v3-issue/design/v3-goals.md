# coder-loop v3 业务目标（操作员陈述，2026-07-02）

> 本文件是操作员在 2026-07-02 总控会话中陈述的 v3 目标的忠实记录（近逐字）。这是 v3 设计的最高权威输入；与任何既有 issue（含 #413）冲突时，以本文件为准，但冲突本身要作为决策点向操作员呈报，不得默默取舍。

## 定位

> coder loop 本质上是一个通用的 AI agent 迭代器，现在聚焦于代码。

## 目标 1：GUI

> v2 已经 daemon 化，但是 v2 的可观测性很弱，每次都是 agent 去找 session 看。假如存在一个好的 web GUI，则看一眼就知道跑没跑。所以我希望 v3 有 GUI，GUI 的设计需要同时考虑 PC 和移动端，GUI 除了做全链路展示，还得有 prompt 展示。

## 目标 2：可并行任务——类 PL 的任务语义设计

> 安全的任务设计有点像 PL 的设计，除了依赖之外还应该有平行函数，所以 v3 加入了可并行任务。这部分需要完整的独立思考到底应该是什么样，而不只是并行这么简单。

## 目标 3：全链路类型化——可计算的状态机判定

> 因为全链路类型化，所以状态机的判定来源是可计算类型，所以不需要运行时验证，元信息本身是可计算的。我认为这部分需要 GUI 可预览。

## 目标 4：零原语纯 meta 定义复杂任务 + CLI context 共享

> 因为类型可计算，所以只需要定义字符串就可以做复杂任务。现在只是 iter+review 循环，我的目的是想要不预先定义任何原语，仅凭 meta 就能做到。iter 实际上是三个不同的阶段，其中两个阶段并行做两个不同的事情。然后可选的 prompt 要求必须调用某种特殊定义的 CLI 工具用于 context 共享，这样独立运行的无状态 agent 也有一定程度上的 context 传递能力。

（注意：这里包含 phase 级并行——"iter 是三个阶段其中两个并行"；与目标 2 的 item/任务级并行是两个层次，任务模型设计须同时覆盖。）

## 目标 5：生命周期 + hook

> 我希望存在生命周期，这样可以挂脚本在 hook 上，这是为了更复杂的可扩展任务机制。举例一个场景：daemon 每一次运行都可以去跑某个脚本，跑脚本会把元数据都传进去，然后 hook 可以计算迭代进行了几轮。为了防止代码腐化，首先插队单独的全面检查代码任务，如果有问题继续插队由这个任务派生的修复任务，然后才继续。这种 gate 怎么设计是后来人自己设计，程序要提供这种接口和能力。

## 目标 6：第三方调用接口 + GitHub 外挂

> v3 我希望加入一种和 GitHub 耦合的可选功能，这个应该是外挂，而不是 coder loop 自己的原生功能。现在的 iac 存在监听 GitHub webhook 自动打开 agent session 去部署，v3 我想要有类似的能力。coder loop 自己预留第三方调用的机会以适应任何形态的外部系统。对于第三方 daemon 来说，传递的值不是某个 prompt，而是选定某个链，或者独立的 workspace，并且选择工作流程并提供元信息。

## 工作方法（操作员指定）

> 我不可能同时回答这么多决策问题，这是非常庞大的设计。总控会话准确把握现有代码和 issue 以及业务目标，规划并拆分 RFC；然后 RFC 的核心内容和议题的调查，用 hapi open session 交给别的 Claude 继续。这样操作员在不同会话中回答不同层次的设计决策，AI 也更容易保持注意力。RFC 的 issue 编写由各子会话完成，不由总控做。
