# Quality: evidence

Evidence rules — bind executor outputs and orchestrator judgment as one contract. Executors satisfy the constraints; orchestrators judge reports against the same constraints.

## Constraints and judgment

- **Environment setup is part of execution — auth and binaries included.** A fresh worktree has nothing installed: before running any project command, perform the setup yourself — dependency install per manifest/lockfile, required build steps, env files the workflow file describes. Missing binaries you install. Missing credentials: every deliverable falls into two cases and both have auth by construction — a standalone program you spin up (mint the auth: create test user / generate local token as part of starting it), or a plugin/extension of an IaC-provisioned service (usable auth already exists on this machine — keychain, tool config/dotfiles, project secret paths; resolve it). "No auth" and "no binary" are **never** reportable blockers — they are setup you have not finished. The only residual blocker is an external service genuinely unreachable after setup — reported with the setup commands you attempted and their output.
- **E2E is direct-run.** Every code deliverable ships e2e evidence produced by **directly running the real thing**: a program/CLI/daemon → invoke its real entry point the way an operator would (real arguments, real config); a web app → drive the real UI end-to-end with agent-browser (enter, operate, observe the persisted result). "It is a library" is not an exemption — run its real consuming surface. **Script e2e is forbidden**: a harness wrapping the calls is integration testing whatever its filename. Unit and integration tests must exist and pass, but they are supporting layers — never the formal deliverable evidence. The direct run's runtime traces (command transcript, service logs, browser screenshots) are the evidence.
- **Runtime manifest, environment stays up.** Record everything the run needed, precisely enough that review can re-run from it alone: binaries (+ how installed), services and start commands, credentials **by resolution location only** (keychain entry name, config path — never the secret value anywhere), ports, env vars, fixtures. When your step started the deliverable's runtime for e2e, **leave it standing** and document it (PIDs, ports, log paths, stop commands) — teardown belongs to review, not to you. A secret value pasted into any report is a hard fail — locations only.
- **Real path only.** Evidence must come from the real system: real dev server, real CLI invocation, real browser session, real service, real DB. Mocks, stubs, fakes, in-memory substitutes, and recorded replays never count as end-to-end evidence. If the real path cannot run, record the exact command, failure mode, exit status, and log excerpt as a blocker — do not substitute a weaker path and present it as the real one.
- **Log evidence is text.** Command output, test results, build logs, and runtime logs go into evidence as text: command + exit status + concise excerpt or path to the full log. Do not screenshot terminal output or locally rendered logs.
- **Screenshots show the real system.** A valid screenshot captures the actual running dev server, CI dashboard, service UI, or deployed page. Never create a local HTML file that renders logs/data/test results and screenshot it — synthetic screenshots are worthless and rejected. After capturing, verify the file exists under a tracked `screenshots/` path and opens as image data.
- **CI parity.** Detect project CI configuration first. For GitHub Actions jobs reproducible locally, run the relevant job with `act`, deriving workflow path, event, job, and runner architecture from the project. If local CI-parity cannot run (Docker, act install, image pull, network, runner tooling), record the exact command, failure mode, exit status, and log excerpt as an infrastructure blocker. Never silently skip; never substitute remote PR checks.
- **Positive and negative paths.** When the issue scope or target workflow requires it, capture both the path that should now succeed and the path that should now be rejected/fail.
- **Long-running processes.** Every process you start and every temp file you write outside the evidence directory must be listed in your report's problems/side-effects section — the orchestrator cleans from that list.
- **Artifacts under evidence dir.** Save command logs, screenshots, and other artifacts under the run's evidence directory so they survive process exit and are citable by path.
- **Test-inventory delta.** When your step runs the project test suite, also measure the delta against the base branch: total counts on base vs your branch, plus an explicit list of every test that was removed, renamed, skipped, or weakened (empty list stated as empty). The counted integer is the runner's own aggregated summary (`bun test`'s `Ran N tests`, jest/vitest's `Tests:` sum, cargo test's passed+failed+ignored), not an `rg`/`grep` static count of `test(` / `it(` declarations — static counts drift across hosts. Base side is measured in a detached scratch worktree (`git worktree add --detach <SCRATCH>/<role>-base <base-sha>`), install deps there, run the same canonical command, then `git worktree remove` it. Publish as: `Test inventory delta: base <N> tests (command: <cmd>; log: <path>); head <N> tests (command: <cmd>; log: <path>); removed/renamed/skipped/weakened: <list or "none" after explicit enumeration>`.

## What to reject in reports

- Every success claim needs its observation — command with exit + output, or an artifact. A claim without observation is a gap.
- Weak signals (`is-active: active`, HTTP 200 without body analysis, `Apply complete!`, whole-suite pass counts alone, type-check/build success) prove tooling ran — not that the issue's behavior holds. Landing-check layer only; never end-to-end acceptance.
- Every artifact/log excerpt must tie to a specific behavior or acceptance row. Unmapped log pile is not an evidence packet.
- Evidence that is missing, stale (only on main / deleted branches), local-only when review must consume it from GitHub, or unopenable is insufficient regardless of surrounding prose.
- Real-path admitted absent → the corresponding acceptance rows are unmet, however complete the rest of the packet looks.
- E2E from a script/harness → treat the e2e as absent, however green.
- "No auth" / "no binary" claims are rejected outright — auth exists by construction; a report claiming otherwise has skipped setup.
- A report covering a test-suite run without the base-vs-branch inventory delta is incomplete. A delta whose integer comes from a static source scan, or whose base side was measured by swapping the checkout, is a protocol violation. Simple integer mismatch between iteration's publish and review's re-measurement is not automatic credibility failure when both sides followed the protocol — route to investigation of runner logs and push history (evolving HEAD, dependency drift) first.
